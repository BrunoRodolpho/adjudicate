# ADR-133 — Red Team history surface

- **Status:** Accepted
- **Date:** 2026-06-07
- **Scope:** `@adjudicate/red-team` (`digestRedTeamReport` + `runRedTeamAcrossPacks` + `createInMemoryRedTeamHistoryStore`; `RedTeamRunRecord`/`RedTeamTrendPoint`/`RedTeamHistoryView`/`RedTeamHistoryQuery`/`RedTeamHistoryStore`/`RedTeamHistoryOptions`), `@adjudicate/admin-sdk` (`governance.redTeamHistory`; `RedTeamRunRecord`/`RedTeamTrendPoint`/`RedTeamHistoryResult` schemas + `RedTeamHistoryQuery`; `AdminContext.redTeamHistory?`), apps/console (unified `/red-team` page), apps/web (public red-team defenses badge).
- **Related:** ADR-118 (`@adjudicate/red-team` — `runRedTeam`/`generateAllVectors`/`computeRedTeamExitCode`/`taintEscalationCausality`/`RedTeamReport`, deterministic seed, "Invariants preserved" — red-team is a pure consumer of the existing taint/auth/business vocabulary), ADR-128 (cross-cutting web-parity platform / dual-app transparency contract + chart kit). Design doc: `docs/roadmap/design/red-team-results.md`.

## Context

The red-team surface (ADR-118) computed `runRedTeam(...)` **once at module load** against a single hard-coded Pack (`deploymentsApprovalPack`) and threaded one `RedTeamReport` into `AdminContext.redTeamReport`; `governance.redTeam` returned that snapshot and `RedTeamPanel` rendered defended/escaped/errors + a per-vector escape table. Two gaps: there was **no run history** (the report is recomputed on every cold start and never persisted, so "trend analysis" had no data source) and **no multi-pack aggregation** (only the first wired Pack was exercised; `PackRegistry` holds five). The roadmap asks the console to show, per Pack, an attack-category breakdown by vector, pass/fail counts, AND a trend over runs. WS3 web-parity also requires a sanitized public red-team status.

## Decision

- **`@adjudicate/red-team` — three additive PURE helpers** (additive MINOR):
  - `digestRedTeamReport(report)`: a deterministic `0x…` CONTENT digest (canonical-JSON sha256 via `@adjudicate/canonical`) over a canonical projection of the report's meaningful fields — pack id, per-result `name`+`vector`+`status` (sorted by name+vector so insertion order never perturbs the digest), and the summary counts. It deliberately EXCLUDES any timestamp and reads neither `basisCodes`/`decision`/`error` (evidence of HOW a scenario resolved, not WHETHER the posture changed) nor the `at` of a run. Two identical-policy runs collide to one digest regardless of when they ran.
  - `runRedTeamAcrossPacks(packs, opts)`: runs the full suite (`generateAllVectors` → `runRedTeam`) against many packs, returning one `RedTeamReport` per pack in input order. Deterministic; no wall-clock/RNG.
  - `createInMemoryRedTeamHistoryStore({ capacity? })`: a bounded, deterministic run-history store. `record(report, at)` appends one immutable `RedTeamRunRecord = { digest, at, packId, summary }`, stamped with a CALLER-SUPPLIED `at`, IDEMPOTENT on `(packId, digest)` (re-recording the same content is a no-op — a cold-start replay never duplicates a run), with a per-pack FIFO ring (default capacity 500, oldest evicted first). `view(query?)` returns `{ runs, trend }` — runs newest-first per pack (optionally filtered by `packId` / windowed by `limit`) plus a chronological `RedTeamTrendPoint[]` (`at, packId, total, defended, escaped, errors`).
- **`@adjudicate/admin-sdk` — `governance.redTeamHistory`** (additive MINOR): a `.query(RedTeamHistoryQuerySchema)` (`{ packId?, limit? }`, `limit` capped at 500) → `RedTeamHistoryResultSchema` (`{ runs: RedTeamRunRecord[], trend: RedTeamTrendPoint[] }`). `RedTeamRunRecordSchema` reuses the frozen `RedTeamSummarySchema` and constrains `digest` to `/^0x[0-9a-f]+$/` and `at` to ISO datetime. Schemas re-declare the `RedTeamHistoryView` shape as Zod with NO dependency on `@adjudicate/red-team` — the same dependency-free posture `RedTeamReportSchema` (ADR-118) takes. New `AdminContext.redTeamHistory?: { view(input): RedTeamHistoryResultParsed }`; PRECONDITION_FAILED when absent — identical runtime feature-detection to `redTeamReport`/`governance.redTeam`. `governance.redTeam` is unchanged.
- **Console:** a unified `/red-team` page (new Sidebar item "Red Team", `Swords`) with three clearly-labelled sub-views — **Pass / fail** (defended/escaped/error counts + a per-vector escapes table, from `governance.redTeam`; a non-zero escape is red), **Attack categories** (scenario count per attack vector via `<BarDistribution>`, including zero-count vectors), and **Trend** (defended vs escaped per recorded run via `<StackedAreaChart>` from `governance.redTeamHistory`, with a newest-first run table carrying short digests). The existing governance `RedTeamPanel` stays where it is; `/red-team` is the unified home.
- **Console route wiring:** the reference console computes the CURRENT run across every installed Pack — `runRedTeamAcrossPacks` over `PackRegistry.all()` — and records each into the history store with an evenly-spaced ISO timestamp derived from a FIXED base (`2026-01-01`, ~one-quarter step) — no wall-clock, so the history is byte-stable across restarts. To make the Trend legible in the reference demo, a small number of ILLUSTRATIVE prior history entries (earlier fixed timestamps, slightly varying defended counts — a dip that recovers) are seeded, CLEARLY labelled illustrative in code; the LATEST point recorded per pack is the REAL current run. A production deployment records only real runs (e.g. one per CI release-candidate). The existing single `redTeamReport` wiring is intact.
- **Web:** a public, read-only `/transparency/red-team` "Defenses" card per shipped pack, fed by a committed *illustrative* fixture projected through the **aggregate-only, banded** `projectRedTeamDefenses` — only `total` + `defended` counts and a BOOLEAN `lastRunStatus` (clean when defended === total, regressed otherwise). No scenario names, attack payloads, basis codes, decisions, error strings, `escapesByVector` maps, or raw escape/error counts ever cross the boundary. Linked from `/transparency` ("Red-team defenses" card).

## Why this shape

- **Additive, pattern-matched.** The producer helpers are additive on `@adjudicate/red-team`; `governance.redTeamHistory` mirrors the established context-read + PRECONDITION_FAILED idiom (sibling to `redTeam`); the SDK schema carries no `@adjudicate/red-team` dependency, exactly like `RedTeamReportSchema`. No new kernel change, no producer-vector change.
- **Determinism by construction.** `digestRedTeamReport` reads only report content; `record(report, at)` is a pure, content-keyed, idempotent append; the per-pack ring's FIFO eviction is total. The package calls neither `Date.now()` nor RNG — timestamps are caller-supplied, mirroring the kernel rule that the harness owns time. The console replay derives its stamps from a fixed base.
- **Digest = content, not timing.** Because the digest excludes `at`, replaying the same policy yields the same digest → the store treats it as the same run (idempotent). A trend point appears only when the *content* changes (a regression or a fix), not on every cold start — which is what makes the trend meaningful. A reviewer can re-derive any row: re-run the pack at its seed, recompute `digestRedTeamReport`, and assert equality to the stored `digest`.
- **Public-leak defense in depth.** A `RedTeamReport.results[]` entry carries `name` (telegraphs attack construction), `basisCodes` (a map of which defense fired — a roadmap for probing gaps), `decision`, `acceptable`, and `error` (may embed internals). The public projection is an allowlist whose output type cannot even carry any of those, a per-vector breakdown, or a raw escape count — only two counts + a clean/regressed band per shipped pack.

## Invariants preserved

- **Outside the determinism/taint boundary.** Red-team is a pure consumer of the existing taint/auth/business vocabulary (ADR-118); it only *asserts* the taint gate fires and never mutates the lattice. Nothing here reaches `intentHash`/`adjudicate()`/policy/state. The history store is in-process telemetry, never a system of record — loss or tampering degrades observability only; the durable, hash-chained audit ledger remains the governance source of truth.
- **Bounded cardinality.** Retention is capped per pack at `capacity` (default 500), oldest evicted first. Each retained record is a fixed-shape `{ digest, at, packId, summary }` — total retained payload is bounded.
- **No closed-enum widening.** `AttackVector` (3) and `RedTeamStatus` (3) are unchanged; the SDK reuses the frozen `RedTeamSummarySchema` for the per-run summary. No new `GovernanceEvent` taxonomy — runs are telemetry, never an audit field. No kernel/wire/canonical-hash change. Additive MINOR on `@adjudicate/red-team` and `@adjudicate/admin-sdk`.

## CI angle

`runRedTeamAcrossPacks` over all shipped Packs is the natural CI gate: a release-candidate step runs the suite across `PackRegistry`, feeds `computeRedTeamExitCode` (exit 2 on any escape/error — a hard release gate, not a percentage), and can record each report into a history store (or emit a `red-team-history` artifact) so the trend accumulates one real point per RC. The SLO is `escaped + errors == 0` on every Pack at every RC run; a trend regression alert fires when a Pack's `defended` drops vs the previous digest.

## Test coverage

`packages/red-team/tests/history.test.ts` — digest (0x-hex, stable across equal reports, order-invariant, timing-excluded, ignores basisCodes/decision/error, flips on a status change / different pack id); `runRedTeamAcrossPacks` (one report per pack in order, byte-identical to manual mapping, [] for none); store (record with supplied `at`/digest/packId/summary, idempotent on (packId, digest), distinct run on content change, newest-first per pack, per-pack partition + first-seen order, packId filter); capacity/eviction (FIFO past capacity per pack, default 500, floor non-positive, `limit` windowing, reset); trend derivation (one chronological point per run, deterministic over the same (report, at) sequence, digest ties to the produced report). `packages/admin-sdk/tests/red-team-history-trpc.test.ts` — schema round-trips + 0x/ISO guards + `limit` bounds; `governance.redTeamHistory` (runs+trend, packId filter, `limit` windowing, PRECONDITION_FAILED, no `redTeam` regression). Console `/red-team` page component test (pass/fail summary clean=emerald / regressed=red + per-vector escapes; attack-category counts incl. zero-count vectors; trend chart + newest-first run table with short digests; empty/loading/error states for report and history independently). Web `red-team-transparency` projection test (banded aggregate clean/regressed, clamps tampered defended, deterministic, allowlisted keys only, drops injected scenario name / basis code / payload / vector map / escape count).

## Lifecycle

New `@adjudicate/red-team` symbols (`digestRedTeamReport`/`runRedTeamAcrossPacks`/`createInMemoryRedTeamHistoryStore` + `RedTeamRunRecord`/`RedTeamTrendPoint`/`RedTeamHistoryView`/`RedTeamHistoryQuery`/`RedTeamHistoryStore`/`RedTeamHistoryOptions`) and `@adjudicate/admin-sdk` symbols (`governance.redTeamHistory`; `RedTeamRunRecordSchema`/`RedTeamTrendPointSchema`/`RedTeamHistoryResultSchema`/`RedTeamHistoryQuerySchema` + inferred types; `AdminContext.redTeamHistory?`) ship in the combined WS3 MINOR wave with `.changeset/red-team-history.md` and V1_FREEZE_MATRIX rows (added in the Phase-E backfill — not in this PR). The existing ADR-118 red-team rows are unchanged. Console/web are app-only. The `projectRedTeamDefenses` allowlist is an app-level contract in `apps/web`: any new field must be consciously added with a "is this safe to publish?" sign-off.
