feat(approval-engine,adjutant): 072 — separation-of-duty (approver != proposer != agent). Today the approval pipeline records who RESOLVED a request (`resolvedBy`) but never records who PROPOSED it, so no `approver != proposer != agent` comparison was possible anywhere in `@adjudicate/approval-engine` (a grep for `proposer|self.approv|approver !=|requestedBy` over `src/` returned zero matches). This plan adds a proposer/initiator binding to the approval request and a fail-closed self-approval guard at resolve time, while leaving the kernel override (`core/src/kernel/adjudicate-and-audit.ts`) and the upstream single-use `confirmationStore.take()` defense (`adapter-core/src/loop.ts`) BYTE-UNCHANGED — the kernel remains the sole authority (§B single-authority, §D-1). The SoD proposer identity is deliberately kept OFF the kernel `confirmationReceipt` (071's optional capability/approver/channel bindings stay byte-identical) and OUT of the `intentHash` pre-image, so §D-4 (intentHash recipe) and the additive-determinism fence are preserved; enforcement is engine-side only (§D fence — the new guard runs in the impure engine shell, never the pure kernel). Fail-closed by construction (§C monotonicity, §D-6): an unresolvable / missing identity REJECTS, never approves.

- **`@adjudicate/approval-engine` (`src/registry.ts`):** add the additive optional `ApprovalRequest.requestedBy?: { id; displayName? }` proposer (maker) projection field — a DISPLAY/GOVERNANCE field only, captured at request-creation, never on the kernel receipt or in the intentHash (T1).
- **`@adjudicate/approval-engine` (`src/registry-redis.ts`):** the redis projection serializes the whole `ApprovalRequest`, so `requestedBy` round-trips automatically; the module docblock's display-field list now names it (the documented GET+SET display-only TOCTOU race semantics are unchanged) (T2).
- **`@adjudicate/approval-engine` (`src/engine.ts`):** add the fail-closed self-approval guard inside `withTokenLock` in `resolve()`, AFTER the `UNKNOWN_TOKEN`/`ALREADY_RESOLVED`/attestation gates and BEFORE quorum accumulation and `agent.confirm()` — so a maker self-vote never even counts toward quorum and never reaches confirm (T3). Gated behind the new `ApprovalEngineOptions.enforceSeparationOfDuty` flag (default OFF = rollback flag, §7) with an optional `agentIdentity` for the `approver != agent` leg. When enabled, an ACCEPTED resolve is rejected with `ApprovalError("SELF_APPROVAL_FORBIDDEN")` if (a) the approver id is missing/unresolvable, (b) the request captured no `requestedBy`, (c) the approver id equals the proposer id, or (d) the approver id equals the configured agent identity. A DECLINE is never blocked (a decline never authorizes). The resolving approver id is the cryptographically-verified `attestation.approverId` when attestation is enforced, else `input.by.id` (an attestation id without a configured verifier is treated as absent → fail-closed). `request()` now accepts an optional `requestedBy` captured onto the projection.
- **`@adjudicate/approval-engine` (`src/governance.ts`):** extend `quorumMet(approvals, policy, proposerId?)` to dedup accumulated approvers against the proposer as well as against each other — a proposer self-vote does not count toward `minApprovals` (applies under both `distinctApprovers` and raw-vote counting). The engine threads `existing.requestedBy?.id` into the quorum check INDEPENDENTLY of `enforceSeparationOfDuty`, so even with the hard guard off a maker cannot count toward their own four-eyes quorum (T4). Omitting `proposerId` is byte-identical to the pre-072 behavior.
- **`@adjudicate/approval-engine` (`src/errors.ts`):** add the typed `SELF_APPROVAL_FORBIDDEN` code to `ApprovalErrorCode` (T5). No new named types need exporting (the field is on the already-exported `ApprovalRequest`, the code on the already-exported `ApprovalErrorCode`, the options on the already-exported `ApprovalEngineOptions`, the param on the already-exported `quorumMet`) (T6).
- **`@adjudicate/adjutant` (`src/orchestrator.ts`):** stamp `requestedBy` on the `ApprovalRequest` at proposal-creation time from the PROPOSING envelope's actor (`{ id: actor.sessionId, displayName: actor.principal }`) WITHOUT threading it into the kernel `confirmationReceipt` — the ops-plane `resolve()` still binds only `{approver, channel}` into the receipt, never the proposer (T7). The override path and the upstream `take()` defense are untouched (T8 — asserted, no edit).

Tests: registry persists + returns `requestedBy` (and omits it when absent) (`approval-engine/tests/registry.test.ts`); redis projection round-trips `requestedBy` (`approval-engine/tests/registry-redis.test.ts`); engine rejects a self-approve fail-closed and never calls `agent.confirm`, rejects the agent identity, rejects a missing approver / missing proposer under enforcement, still allows a maker to DECLINE, allows a distinct approver, and preserves pre-072 behavior when the flag is OFF (`approval-engine/tests/engine.test.ts`); `quorumMet` proposer-dedup unit tests, distinct + raw-vote, byte-identical when `proposerId` omitted (`approval-engine/tests/governance.test.ts`); an in-process accumulated proposer self-vote is recorded but does NOT advance the quorum (`approval-engine/tests/engine-governance.test.ts`); the SoD proposer identity is NOT carried on the kernel receipt/binding and 071's optional bindings stay additive (`core/tests/kernel/confirmation-receipt.test.ts`); the adjutant stamps `requestedBy` from the minting actor and NEVER threads the proposer into the kernel receipt binding (`adjutant/tests/orchestrator.test.ts`). The change is additive behind the optional `requestedBy?` field and the default-OFF `enforceSeparationOfDuty` flag; revert = drop the guard and the field (persisted data stays backward-compatible), kernel + `take()` paths require no migration.
