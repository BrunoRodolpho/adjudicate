fix(approval-engine,adjutant): H7 — make the channel-binding gate MEANINGFUL in both callers (was tautological, always-equal → always-pass). The kernel gate `confirmationBindingMatches` (`@adjudicate/core`) is sound + fail-closed, but both callers fed ONE channel value into BOTH the `requested` and `confirmed` sides, so the equality could never fail and a confirmation arriving on a different channel than its request was minted on could never be caught. The kernel gate, the closed 6-outcome `Decision` algebra, the guard order, and `intentHashInput` are UNCHANGED — the fix is entirely in the two impure callers, and is back-compat (additive), fail-closed, and monotonic (friction only up).

- **`@adjudicate/approval-engine` (`src/engine.ts`):** add an OPTIONAL `channel` to the `resolve()` input — the CONFIRM-time delivery channel. The forwarded kernel `binding.channel` now sources `confirmed` from this confirm-time channel and `requested` from the REQUEST-time channel (`existing.channel`, stamped immutably at `request()`), so a cross-channel confirmation produces `requested !== confirmed` and the kernel REFUSES the override (fail-closed, §D-6). OMITTING `channel` falls back to `existing.channel`, so the equality still holds and the pre-H7 receipt is BYTE-IDENTICAL — a caller that does not yet plumb the confirm-time channel keeps today's behaviour.
- **`@adjudicate/adjutant` (`src/orchestrator.ts`):** the ops plane has EXACTLY ONE confirmation channel (`ADJUTANT_CHANNEL` — a REVIEW proposal is always issued and resolved on it), so no DISTINCT request/confirm channel genuinely exists for this caller. Replace the tautological `{ confirmed: ADJUTANT_CHANNEL, requested: ADJUTANT_CHANNEL }` with a RECORD-ONLY `{ confirmed: ADJUTANT_CHANNEL }` (no `requested`): the channel is still recorded forensically on `supersedes.binding.channel`, but the kernel vacuously satisfies the channel field (a field with no `requested` is recorded-but-not-gated) instead of always-passing a check that could never fail. The approver field (which CAN differ from the proposer) keeps its real gating; the kernel gate is NOT weakened.

Regression test (`packages/approval-engine/tests/engine.test.ts`): a confirm-time channel that DIFFERS from the request channel produces an engine binding with `requested !== confirmed` that the real kernel `confirmationBindingMatches` REFUSES (`false`); a matching channel PASSES (`true`); an omitted channel falls back and PASSES (back-compat). Proven non-vacuous: with the fix reverted the DIFFERS test FAILS (engine emits the tautological pair, gate returns `true`).
